## Jmix

This is a Jmix 3 application. Before writing or changing ANY file in it, read
the `jmix` skill and follow it. It maps the task to artifacts, routes each
artifact to the skill that governs it, and names the checks that close a task.
Your Jmix/Vaadin priors are not reliable here; the skills are.

Managed by the Jmix Agent Toolkit. Content between these markers is replaced on
re-install — put your own instructions outside them.

## Spec-Driven Workflow

### Order

1. **Spec** — write the spec from my prompt.
2. **My review** — stop and wait for my approval. No code before I approve the spec.
3. **Implementation** — follow the `jmix` skill (read the skill for each artifact before writing it).
4. **Review** — review your own diff against the spec.
5. **Verify** — run the gates below.

### Spec location

- Path: `specs/<NN_module>/<NN>-<slug>.spec.adoc`.
- If I don't give a path, derive the module from the topic.
- Modules follow the course lessons:
  - `01_foundations`
  - `02_security`
  - `04_deployment`

### When to skip the spec

Small one-off changes (form defaults, a seed bean): no spec. Implement directly
and tell me what you did.

### What you don't write

- Standard CRUD list/detail views and Liquibase changelogs are generated by
  Jmix Studio, not by you. I generate them.
- If you are unsure how a standard Jmix artifact should look, ask me for a
  Studio-generated sample and repeat it.

### Gates

- **Gate 1** and **Gate 2** — as the Jmix Agent Toolkit says (`jmix` skill).
- **Gate 3** — don't walk the browser yourself. End with a short checklist of
  what I should check in the browser.

### Tests

Only where behaviour is hard to check by hand: security, business rules.

### Safety

- Never run global cleanup commands: `docker system prune`,
  `docker volume prune`, `docker image prune`, `rm -rf` outside the project.
- Remove only what you created, by name.

### Git

Don't commit. I commit after each step.
