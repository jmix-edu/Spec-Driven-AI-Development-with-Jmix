= 04 Floor plan: an image file per floor
:toc: macro
:revdate: 2026-09-30
:status: Approved 2026-09-30

toc::[]

== Goal

An office manager uploads a floor plan (an image) for each floor. An employee sees the plan
of the floor they are booking on, right in the booking form, so they can tell where "Orion"
or desk "2-A-04" actually is.

This is the first file the app stores. So it also covers where files live in `dev` and in
the container, and how they survive a restart.

Prerequisites: `02-views`, `02_security/01-roles` and `04_deployment/01-deployment`
are implemented. `gradle clean test` is green except for the known
`ROOM_AMENITY_LINK` cascade failure, which is tracked separately.

== Scope

.In scope
* `Floor.plan`: a `FileRef` attribute, optional.
* Upload, replace and remove the plan in `Floor.detail` (office manager).
* The plan of the selected room's or desk's floor shown in `Booking.detail` (employee,
  manager read-only, admin), with a download link.
* Captions and messages.
* Role check: the existing roles already cover the attribute. What else the UI needs is
  verified, not assumed (see <<security>>).
* File storage location in `dev` and `prod`, the container volume, and directory
  ownership for the non-root user.

.Out of scope
* Clickable or interactive plans: highlighting the room, placing desks on the image,
  choosing a room by clicking it.
* Plans per building or per room, several files per floor, and version history.
* Removing orphaned files. A plan that is replaced or removed, a floor that is deleted,
  and an upload abandoned by closing the dialog without saving all leave the old file in
  storage. Cleaning up needs an after-commit job (`jmix-add-entity-event-listener`: the
  database cascade gives no event). That is a separate spec.
* Server-side checks of file content (magic bytes, image decoding) and virus scanning.
  The uploader is the trusted office-manager role, and the field restricts types and size.
* Demo data plans. The seeder stays text-only, with no binary assets in the repository.
* Backups of the file volume, and object storage (S3).

== Model

|===
|Attribute |Type |Required |Notes

|`Floor.plan` |`FileRef` |no |Column `PLAN`, `varchar(1024)` (`jmix-create-entity`, file

|===

The changelog is generated by Studio (`addColumn` on `FLOOR_`, nullable, because floors
already exist).

== File rules

* Accepted types: PNG and JPEG (`image/png`, `image/jpeg`, `.png`, `.jpg`, `.jpeg`).
* SVG is *not* accepted. An SVG can carry script, and the plan is shown inline to every
  employee.
* PDF is not accepted, because it cannot be shown inline as an image.
* Maximum size: 10 MB on the upload field. The storage-wide limit
  `jmix.localfs.max-file-size` stays at its 100 MB default.

== Screens

=== Floor.detail (office manager, admin)

* A `fileStorageUploadField` bound to `plan`, with the accepted types and size above. It
  offers upload, replace and clear.
* Below it, a preview of the current plan (the `image` component), hidden when there is
  no plan.
* The floor is a composition dialog inside `Building.detail`. The file reaches the storage
  on upload, and the `FileRef` is saved with the building. See "Out of scope" for
  abandoned uploads.

=== Booking.detail (everyone who can open it)

* Below the form: the heading "Floor plan", the plan image of the floor of the selected
  `room` (or of the selected `desk`), and a download link that opens the original file.
* It updates when the room or desk changes. If neither is set, or the floor has no plan,
  a short text explains that instead of the image.
* The fetch plans of `Booking.detail` extend to `room.floor.plan` and `desk.floor.plan`,
  so the image appears without another query when an existing booking opens.
* The image is read from the file storage through Jmix (`FileStorage` / `Downloader`).
  There are no direct URLs to the storage directory.

This changes a Module 1 screen. It is in scope here because the booking form is the only
screen an employee has.

[[security]]
== Security

* `EmployeeRole` already grants `READ` on `Floor` with `*: VIEW`, which includes `plan`.
  `OfficeManagerRole` grants `ALL` with `*: MODIFY`. No new entity or attribute policies
  are expected.
* Whether upload, image display or download need a Jmix *specific* policy (a
  `@SpecificPolicy` resource) is not known from the docs at hand. It is verified in the
  running app for each persona. Anything missing is added to the role that needs it, and
  recorded in this spec's Decisions.
* An employee sees only plans of floors whose rooms or desks they can pick, which is all
  of them. A plan is not sensitive within the company.

== Storage and deployment

[cols="1,4"]
|===
|Profile |Location

|`dev` |Jmix default under the work directory (`.jmix/work/…`, already git-ignored), no
setting needed.
|`prod` |`jmix.localfs.storage-dir=${FILE_STORAGE_DIR:/app/filestorage}`
|===

* `Dockerfile`: create `/app/filestorage` and `/app/.jmix`, owned by the `booking` user,
  before `USER booking` (`jmix-verify-bootrun`: uploads in a non-root container).
* `docker-compose.yml`: the named volume `booking-files` mounted at `/app/filestorage`,
  so plans survive `docker compose down` and are only removed by `down -v`.
* README: one line on where plans are stored, and that `down -v` deletes them together
  with the database.

== Acceptance criteria

. Gate 1: compile passes, and the inspection is clean on `Floor.java`, `floor-detail-view.xml`,
  `booking-detail-view.xml`, `BookingDetailView.java` and the properties.
. The changelog adds `PLAN varchar(1024)`, nullable, to `FLOOR_`, and nothing else.
. Gate 2: `gradle clean test` shows no new failures (the known `ROOM_AMENITY_LINK`
  failure aside).
. Container (verified by Claude with `docker compose up -d --build`, torn down by project
  name afterwards): the app user can write to `/app/filestorage`, checked with
  `docker exec … touch` as `booking`. The volume `booking_booking-files` exists.
. In the browser (Gate 3, checked by you):
.. As `manager1`, uploading a PNG on a floor shows the preview, and it is still there
   after saving the building and reopening it.
.. As `manager1`, a `.svg`, a `.pdf` and a file over 10 MB are refused by the field.
.. As `manager1`, replacing the plan shows the new image, and clearing it hides the
   preview.
.. As `emp1`, a new booking shows the plan when a room on that floor is picked, and it
   changes when a desk on another floor is picked instead. It shows the "no plan" text for
   a floor without one. Download opens the original file.
.. As `manager1`, opening a booking read-only shows the plan too.
.. In the compose stack, a plan uploaded before `docker compose down` and `up` is still
   shown afterwards.

== Decisions

. Employees see the plan in the booking form. No separate screen.
. PNG and JPEG only, 10 MB.
